# طراحی CODAL — پشتیبان‌گیری و انتقال امن به Google Drive

- مأموریت: `PM-CODAL-ALL-001`
- مرحله: Phase 0
- وضعیت: PROPOSED؛ اتصال Drive در این محیط موجود/تأییدشده نیست
- تاریخ: 2026-11-24

## 1. تصمیم معماری

پایگاه داده فعال روی میزبان مالک باقی می‌ماند. Google Drive مقصد نگهداری اسناد خام و backup نسخه‌بندی‌شده است؛ نه محل اجرای فایل DB زنده. قطعی Drive نباید عملیات خواندن/نوشتن مخزن فعال را متوقف کند.

## 2. جریان پیشنهادی

1. فایل خام در مخزن محلی immutable ثبت و SHA-256 محاسبه می‌شود.
2. metadata و انتقال موردنیاز در صف پایدار ثبت می‌شود.
3. worker انتقال فایل را به مسیر اختصاصی Drive کپی می‌کند.
4. پس از انتقال، checksum/size مقصد در صورت پشتیبانی قابل راستی‌آزمایی است.
5. manifest محلی و نتیجه انتقال ثبت می‌شود.
6. شکست انتقال با retry/backoff و checkpoint باقی می‌ماند.
7. backup پایگاه داده به‌صورت snapshot سازگار/مجاز ساخته، رمزگذاری و سپس منتقل می‌شود.
8. دوره‌ای restore drill در مسیر جدا انجام می‌شود.

## 3. ابزار و قواعد پیشنهادی

rclone گزینه قابل ارزیابی برای انتقال است؛ هنوز انتخاب و نصب نشده است.
- ترجیح `copy` برای کپی افزایشی؛ از `sync` و `move` تا طراحی حفاظت حذف و تأیید مالک استفاده نشود.
- انتقال دوطرفه عمومی و خودکار توصیه نمی‌شود؛ منبع حقیقت برای هر نوع فایل باید صریح باشد.
- برای اسناد خام، جریان اصلی local → Drive است.
- Drive → local فقط برای دریافت ورودی‌های دستی مجاز و با manifest/قرنطینه و بررسی hash.
- از قرار دادن فایل SQLite فعال در پوشه sync خودداری شود.
- credential فقط روی میزبان و با حداقل scope؛ هرگز در Git، log یا فایل قابل اشتراک ثبت نشود.

## 4. Manifest پیشنهادی

هر مورد انتقال:
- transfer_id و mission_id
- local object id/path
- Drive file id/path (پس از دسترسی)
- file size و SHA-256
- content type
- created_at، queued_at، transferred_at، verified_at
- direction و source-of-truth
- attempt count و آخرین خطا
- encryption/key reference (بدون ذخیره secret)
- status: QUEUED, COPYING, COPIED, VERIFIED, RETRY_PENDING, FAILED

## 5. رفتار قطعی و تعارض

- خطای شبکه یا quota: نگه‌داری در صف و ادامه سرویس محلی.
- hash ناسازگار: قرنطینه و توقف تأیید آن فایل؛ overwrite ممنوع.
- فایل موجود با محتوای متفاوت: ایجاد نسخه جدید، نه overwrite خاموش.
- حذف در Drive: به‌صورت خودکار به حذف محلی سرایت نکند.
- فایل ورودی از Drive تا بررسی malware/type/hash و اعتبار منبع، داده قابل اعتماد محسوب نشود.
- backup رمزگذاری‌شده؛ کلید جدا از backup و خارج از Git نگه‌داری شود.

## 6. محدودیت میزبان فعلی

در بررسی read-only قبلی، میزبان Windows 10 Pro دارای حدود 7.91 GB RAM و SSD حدود 240 GB بود؛ فضای آزاد گزارش‌شده روی C حدود 11.61 GB و D حدود 2.74 GB (در مجموع حدود 14.35 GB) بود. این میزان برای تصمیم نصب DB، نگه‌داری اسناد و backup کافی فرض نمی‌شود. ارقام باید پیش از اجرا دوباره بررسی شوند.

بنابراین:
- نصب PostgreSQL، rclone یا سرویس جدید فعلاً انجام نمی‌شود.
- ابتدا باید ظرفیت واقعی و نیاز نگه‌داری/backup محاسبه شود.
- افزودن دیسک مستقل یا مقصد backup دوم ممکن است لازم باشد.
- روشن‌ماندن و دسترس‌پذیری میزبان باید از مالک پرسیده شود.

## 7. معیار پذیرش

- آزمون قطع Drive و ادامه سرویس فعال.
- آزمون resume پس از قطع وسط فایل.
- آزمون checksum mismatch و جلوگیری از تأیید فایل خراب.
- آزمون نسخه‌بندی و جلوگیری از حذف ناخواسته.
- backup و restore واقعی در محیط آزمایشی.
- ثبت audit و گزارش backlog/failed transfer.
- آزمون دسترسی حداقلی و عدم افشای credential.

## 8. موارد باز

- تأیید دسترسی Google Drive و انتخاب پوشه مقصد اختصاصی.
- تعیین retention و تعداد نسخه backup.
- تعیین مقصد backup دوم و سیاست رمزگذاری/مدیریت کلید.
- تأیید ظرفیت دیسک و وضعیت always-on میزبان.
- انتخاب نهایی rclone یا ابزار جایگزین پس از ارزیابی امنیت و قابلیت‌ها.

## 9. وضعیت

هیچ فایل یا داده‌ای در Drive خوانده، نوشته یا منتقل نشده است. این سند فقط طراحی پیشنهادی است.
