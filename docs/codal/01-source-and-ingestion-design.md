# طراحی CODAL — پرونده منابع و دریافت اطلاعات

- مأموریت: `PM-CODAL-ALL-001`
- مرحله: Phase 0 — بررسی و طراحی فقط
- وضعیت: PROPOSED / شواهد فنی منبع نیازمند تکمیل
- تاریخ تهیه: 2026-11-24
- مرجع پذیرش: مالک پروژه

## 1. هدف و مرز

طراحی مخزن جامع و مستقل اطلاعات افشای شرکت‌های پذیرفته‌شده در بورس تهران و فرابورس ایران، با اتصال کنترل‌شده به ARYA AI Trader. این سند مجوز ساخت crawler، دانلود انبوه، استخراج یا ذخیره‌سازی عملیاتی نیست.

## 2. اصول غیرقابل مذاکره

1. داده فقط با منبع قابل ردیابی پذیرفته می‌شود؛ مقدار حدسی یا تولیدشده توسط مدل زبانی ممنوع است.
2. سند خام دریافتی تغییرناپذیر است؛ اصلاحیه، نسخه جدید و استخراج مجدد رکورد جدید ایجاد می‌کنند.
3. زمان انتشار منبع، زمان دریافت و زمان اثرگذاری داده جدا نگه داشته می‌شوند.
4. هر داده استخراج‌شده باید به سند و محل دقیق آن (صفحه/جدول/ردیف/سلول یا شناسه بخش) قابل ردیابی باشد.
5. شکست یا عدم دسترسی CODAL نباید دسترسی ARYA به داده‌های قبلاً ثبت‌شده را مختل کند.
6. روش دستی و خودکار باید به یک قرارداد داده و مسیر ممیزی مشترک وارد شوند.
7. Drive مخزن اسناد خام و نسخه پشتیبان است، نه پایگاه داده فعال.

## 3. دامنه محتوایی پیشنهادی

| خانواده | نمونه اطلاعات | وضعیت دامنه |
|---|---|---|
| صورت‌های مالی | سالانه، میان‌دوره‌ای، تلفیقی و جداگانه، یادداشت‌ها | پیشنهادی؛ نیازمند فهرست نهایی انواع اطلاعیه |
| فعالیت ماهانه | تولید، فروش، مقدار، نرخ، درآمد، تفکیک محصول | پیشنهادی |
| مجامع | عادی، فوق‌العاده، تصمیمات و زمان‌بندی | پیشنهادی |
| سرمایه | افزایش سرمایه، حق‌تقدم، ثبت و مراحل | پیشنهادی |
| رویدادهای بااهمیت | گروه الف/ب و سایر اطلاعیه‌های بااهمیت | پیشنهادی |
| قراردادها و دعاوی | انعقاد/فسخ قرارداد، دعاوی و آثار اعلام‌شده | پیشنهادی |
| سایر افشاها | توقف/بازگشایی، تغییرات، شفاف‌سازی و اصلاحیه‌ها | طبقه‌بندی دقیق نیازمند بررسی |

این جدول فهرست نهایی و جامع انواع کدال نیست. طبقه‌بندی نهایی باید از فهرست رسمی انواع اطلاعیه و نمونه واقعی استخراج و با مالک تأیید شود.

## 4. روش دریافت پیشنهادی

- **کانال اصلی:** رابط/صفحات رسمی CODAL پس از شناسایی مستند و آزمون مستقل.
- **کانال جایگزین:** دریافت دستی فایل توسط مالک یا اپراتور مجاز و ثبت همان metadata و provenance.
- **ورودی‌های احتمالی:** فهرست نمادها، فهرست اطلاعیه‌ها، جزئیات اطلاعیه، فایل ضمیمه و اصلاحیه/ابطال.
- **محدودیت فعلی:** endpointها، پارامترها، pagination، rate limit، شناسه پایدار اطلاعیه، قرارداد فایل‌ها و سیاست دسترسی هنوز در این مرحله مستقلاً تأیید نشده‌اند؛ همگی `UNVERIFIED` هستند.
- هیچ endpoint، کلید یا رفتار API در این سند به‌عنوان واقعیت تأییدشده معرفی نمی‌شود.

## 5. پرونده شواهد موردنیاز برای هر endpoint

برای هر عملیات باید این جدول تکمیل شود:

| فیلد | الزام |
|---|---|
| URL و method | عین منبع رسمی/ترافیک مشاهده‌شده |
| پارامترها و نوع داده | نمونه معتبر و مرزهای مجاز |
| pagination و ترتیب | آزمون صفحه اول/آخر و تکرار |
| شناسه اطلاعیه | پایداری در برابر اصلاحیه و تغییر عنوان |
| زمان‌ها | timezone، قالب و معنای هر timestamp |
| فایل‌ها | MIME، اندازه، checksum و نحوه دانلود |
| محدودیت دسترسی | rate limit، timeout، خطا و شرایط استفاده |
| مدرک | تاریخ مشاهده، نمونه پاسخ خام، hash و روش بازتولید |
| وضعیت | VERIFIED / PARTIAL / UNVERIFIED / REJECTED |

## 6. گردش‌کار ingest

1. کشف نماد/اطلاعیه و ثبت رکورد کشف.
2. دریافت پاسخ و فایل خام با retry محدود و backoff.
3. محاسبه SHA-256 و ذخیره نسخه خام به‌صورت immutable.
4. ثبت metadata و شناسه منبع.
5. تشخیص نوع اطلاعیه و انتخاب extractor نسخه‌بندی‌شده.
6. استخراج facts همراه با محل دقیق در سند.
7. کنترل واحد، دوره مالی، مقیاس، ارقام و سازگاری.
8. ارجاع موارد کم‌اطمینان/مبهم به صف بازبینی انسانی.
9. انتشار فقط داده‌ای که از gate کیفیت عبور کرده است؛ سایر موارد با وضعیت روشن نگه داشته شوند.
10. ثبت رویداد، شمارش ورودی/موفق/ناموفق/در انتظار و امکان replay.

## 7. سیاست خطا و تداوم

- دریافت باید idempotent و قابل ادامه از checkpoint باشد.
- قطع ارتباط نباید باعث ثبت ناقص به‌عنوان موفق شود.
- حذف یا عدم وجود یک اطلاعیه در فهرست بعدی به‌تنهایی مجوز حذف نسخه قبلی نیست.
- شکست منبع اصلی، حالت دستی را فعال می‌کند؛ داده دستی نیز باید فایل/منبع، ثبت‌کننده و زمان ورود داشته باشد.
- اختلاف دو منبع یا دو استخراج باید به discrepancy تبدیل شود، نه overwrite خاموش.

## 8. معیار پذیرش مرحله طراحی منبع

- نمونه‌های واقعی از تمام خانواده‌های اطلاعیه مورد توافق گردآوری و طبقه‌بندی شده باشند.
- قرارداد endpointها و نمونه‌های خام با تاریخ و hash ثبت شده باشد.
- شناسه پایدار و رابطه اصلاحیه/ابطال با شواهد مشخص شود.
- فهرست نمادها با مرجع رسمی، همراه با تاریخ مبنا و وضعیت نمادها تعریف شود.
- محدودیت دسترسی و روش جایگزین مستند باشد.

## 9. موارد باز برای مالک

- مرز universe: فقط نمادهای فعال یا تمام نمادهای فعال، متوقف، تعلیق‌شده و حذف‌شده در بازه تاریخی؟
- بازه تاریخی اولیه: پیشنهاد قبلی یک سال شناور بر مبنای تاریخ انتشار بوده؛ تاریخ آغاز/پایان باید صریحاً تصویب شود.
- آیا تمام خانواده‌های اطلاعیه از ابتدا در دامنه‌اند یا اولویت‌بندی مرحله‌ای لازم است؟
- سیاست دریافت اطلاعیه‌های محرمانه/دسترسی‌محدود و حدود مجاز استفاده باید تعیین شود.

## 10. وضعیت منابع

در این مرحله اتصال زنده CODAL و Drive انجام نشده است. لینک‌های رسمی و endpointهای عملیاتی باید در مرحله بعد با شواهد اولیه تکمیل شوند. هیچ داده‌ای در این طراحی به‌عنوان داده دریافت‌شده معرفی نمی‌شود.
