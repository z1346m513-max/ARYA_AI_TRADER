# طراحی CODAL — اصلاحیه، ابطال و تاریخچه نسخه‌ها

- مأموریت: `PM-CODAL-ALL-001`
- مرحله: Phase 0
- وضعیت: PROPOSED
- تاریخ: 2026-11-24

## 1. هدف

حفظ تاریخچه کامل اطلاعیه‌ها و اطمینان از اینکه اصلاحیه یا ابطال، نسخه قبلی را بی‌صدا پاک یا بازنویسی نمی‌کند. کاربر باید بتواند هم «آخرین وضعیت شناخته‌شده» و هم «آنچه در یک تاریخ مشخص در دسترس بوده» را بازیابی کند.

## 2. مفاهیم مستقل

- **Disclosure identity:** اطلاعیه منطقی/اصلی.
- **Disclosure version:** هر مشاهده یا نسخه محتوایی مستقل.
- **Raw document:** بایت‌های دقیق فایل دریافت‌شده، با hash.
- **Revision relation:** رابطه نسخه جدید با نسخه قبلی.
- **Knowledge time:** زمان دریافت/شناخته‌شدن نسخه توسط سامانه.
- **Business effective time:** زمان اثرگذاری اعلام‌شده، اگر منبع ارائه کند.

این مفاهیم نباید صرفاً از روی تغییر عنوان یا تاریخ حدس زده شوند.

## 3. روابط پیشنهادی

- ORIGINAL: نسخه اولیه.
- AMENDS: نسخه جدید، نسخه قبلی را اصلاح می‌کند.
- CANCELS: اعلام ابطال/لغو نسخه یا اطلاعیه قبلی.
- REPLACES: نسخه جدید جایگزین نسخه قبلی طبق تصریح منبع.
- DUPLICATE_OF: محتوای تکراری یا بازنشر؛ فقط پس از اثبات.
- RELATED_TO: ارتباط دارد اما رابطه اصلاحی اثبات نشده است.

اگر CODAL رابطه صریح ندهد، رابطه در وضعیت UNVERIFIED می‌ماند و نباید خودکار به AMENDS تبدیل شود.

## 4. قواعد ذخیره‌سازی

1. هر دریافت، با metadata و hash ثبت می‌شود.
2. اگر hash برابر نسخه قبلی باشد، می‌توان دریافت تکراری را ثبت کرد ولی raw blob را deduplicate کرد؛ تاریخ مشاهده و رویداد دریافت از بین نرود.
3. اگر hash متفاوت باشد، نسخه جدید ایجاد می‌شود؛ نسخه قبل immutable می‌ماند.
4. رابطه اصلاح/ابطال با source id و شواهد مستند می‌شود.
5. استخراج مجدد با نسخه جدید extractor، raw document را تغییر نمی‌دهد؛ extraction run و facts مشتق‌شده نسخه‌بندی می‌شوند.
6. اصلاح دستی fact، یک correction event با کاربر، زمان، دلیل و مقدار قبل/بعد ثبت می‌کند.
7. حذف فیزیکی یا جایگزینی فایل خام ممنوع؛ retention فقط با سیاست مصوب و audit انجام شود.

## 5. دو پرس‌وجوی ضروری

- **Latest-known view:** آخرین نسخه معتبر با توجه به روابط اصلاح/ابطال تأییدشده.
- **As-known-at view:** نسخه‌ای که تا زمان مشخصی توسط سامانه دریافت و تأیید شده بود.

این دو پرس‌وجو برای بازتولید تحلیل تاریخی و جلوگیری از look-ahead ضروری‌اند.

## 6. مثال مفهومی

| زمان دریافت | نسخه | رابطه | وضعیت |
|---|---|---|---|
| روز اول | V1 | ORIGINAL | ثبت‌شده |
| روز پنجم | V2 | AMENDS V1 | پس از تأیید رابطه |
| روز دهم | V3 | CANCELS V2 | پس از تأیید رابطه |

در این مثال V1 و V2 همچنان در تاریخچه باقی می‌مانند. خروجی جاری بر اساس رابطه معتبر تعیین می‌شود؛ خروجی as-known-at روز سوم همچنان V1 خواهد بود.

## 7. کنترل‌های کیفیت

- زنجیره نسخه نباید cycle داشته باشد.
- هر relation باید مدرک و source locator داشته باشد.
- زمان دریافت باید monotonic event log باشد؛ ترتیب انتشار و دریافت با هم اشتباه نشوند.
- تضاد دو اصلاحیه یا رابطه نامعلوم به صف بازبینی انسانی می‌رود.
- هیچ نسخه‌ای صرفاً به‌دلیل اینکه دیگر در فهرست فعلی منبع دیده نمی‌شود حذف نمی‌شود.

## 8. معیار پذیرش

آزمون‌های طراحی/پیاده‌سازی آینده باید پوشش دهند:
- نسخه تکراری با hash یکسان؛
- اصلاحیه با hash متفاوت؛
- ابطال؛
- دریافت خارج از ترتیب؛
- رابطه نامعلوم؛
- extractor جدید روی سند قدیمی؛
- query در زمان تاریخی؛
- بازیابی کامل تاریخچه پس از backup/restore.

## 9. موارد نیازمند تأیید

شناسه و semantics رسمی اصلاحیه/ابطال در CODAL باید با نمونه واقعی تأیید شود. این سند رفتار واقعی CODAL را فرض نمی‌کند و صرفاً قرارداد پیشنهادی داخلی است.
