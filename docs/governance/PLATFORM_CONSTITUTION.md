# قانون اساسی پلتفرم ARYA AI Trader

**وضعیت:** لازم‌الاجرا برای تمام اعضای تیم، پیمانکاران، ایجنت‌ها و ابزارهای هوش مصنوعی  
**نسخه:** 1.0  
**تاریخ تصویب:** 2026-10-02  
**مالک پروژه/مخزن:** `ziya1346`

## اصل 1 — مرجعیت و تصمیم‌گیری
1. ARYA AI Trader یک پروژهٔ تحت مالکیت و مدیریت مالک مخزن است.
2. تصمیم نهایی دربارهٔ محصول، معماری، اولویت‌ها، پذیرش یا رد تغییرات و انتشار با مالک پروژه است.
3. هیچ عضو تیم یا ایجنتی صرفاً به دلیل دسترسی به کد، حق تغییر این مرجع تصمیم‌گیری را ندارد.

## اصل 2 — منع توسعه بر مبنای اطلاعات غیرمعتبر
1. هیچ کد، مدل، الگوریتم، Provider، قرارداد API، محاسبهٔ مالی یا تصمیم معماری نباید بر پایهٔ اطلاعات نامعتبر، حدس، نقل‌قول بدون منبع یا خروجی تأییدنشدهٔ AI ساخته شود.
2. «مدرک» باید قابل ردیابی باشد: منبع، URL یا شناسه، تاریخ دسترسی، نسخه/commit در صورت وجود، ادعای دقیق و نتیجهٔ اعتبارسنجی باید ثبت شود.
3. برای API و دادهٔ بازار، اولویت با مستندات رسمی ارائه‌دهنده و منبع اولیه است.
4. منابع ثانویه فقط برای کشف/مقایسه استفاده می‌شوند و برای رفتار حیاتی سیستم باید با منبع اولیه یا آزمون مستقل تأیید شوند.
5. خروجی یک مدل زبانی به‌تنهایی منبع معتبر نیست.
6. در صورت نبود شواهد کافی، وضعیت باید «UNVERIFIED / نیازمند شواهد» باشد و پیاده‌سازی متوقف شود.

## اصل 3 — سلسله‌مراتب منابع
از قوی‌ترین به ضعیف‌ترین:
1. اسناد رسمی، API specification و دادهٔ اولیهٔ مالک منبع.
2. استانداردهای رسمی، مستندات رسمی کتابخانه/پروتکل و منابع دانشگاهی داوری‌شده.
3. دادهٔ قابل تکرار از Provider با fixture، checksum یا test مستقل.
4. منابع حرفه‌ای ثانویه با امکان راستی‌آزمایی.
5. پست، فروم، شبکهٔ اجتماعی و محتوای ناشناس فقط به‌عنوان سرنخ، نه مبنای قطعی کد.

هر سند مرجع باید در صورت امکان با metadata، hash، تاریخ تغییر و وضعیت اعتبار ثبت شود.

## اصل 5 — ردپای کامل تغییرات
هر تغییر معنادار باید همزمان دارای این موارد باشد:
- تغییر کد/مستندات؛
- Change Record در `docs/changes/`؛
- ثبت در `docs/governance/CHANGE_LEDGER.md`؛
- دلیل و شواهد قابل ردیابی؛
- آزمون یا توضیح روشن برای اینکه چرا آزمون ممکن نیست؛
- اثرات و ریسک‌های شناخته‌شده.

پیام commit به‌تنهایی جایگزین Change Record نیست.

## اصل 6 — چندایجنتی و شروع کار
هر عضو/ایجنت در ابتدای هر session کاری مکلف است:
1. `AGENTS.md`؛
2. این قانون اساسی؛
3. `STARTUP_CHECKLIST.md`؛
4. آخرین Change Recordها و Ledger؛
5. ADRهای مرتبط
را بررسی کند.

هر ایجنت باید پیش از تغییر اعلام کند که baseline و تغییرات اخیر را بررسی کرده است. عدم دسترسی به این اسناد باید موجب توقف کار شود، نه حدس.

## اصل 7 — Pull Request و ادغام
- تغییر مستقیم در `main` سیاستاً ممنوع است.
- هر تغییر از branch مستقل و Pull Request انجام می‌شود.
- PR باید دلیل، شواهد، تست، اثرات و Change Record را معرفی کند.
- تغییرات جدید پس از review باید دوباره بررسی شوند.
- برای `main` باید تا حد امکان branch protection/ruleset فعال شود: PR اجباری، review مالک، status checks، حل conversationها و جلوگیری از force-push. GitHub این سازوکارها را برای protected branches/rulesets پشتیبانی می‌کند.

## اصل 8 — کیفیت و داده
- تست واحد نباید به شبکهٔ زنده وابسته باشد.
- تست زنده باید جدا و با برچسب smoke/integration اجرا شود.
- داده باید freshness، source و کیفیت قابل ردیابی داشته باشد.
- دادهٔ ناقص نباید به‌طور خاموش به سیگنال مثبت یا تصمیم قطعی تبدیل شود.
- تغییر پارامتر اندیکاتورها، timeframe، وزن‌ها و استراتژی‌ها باید قابل ردیابی و قابل بازتولید باشد.

## اصل 9 — مالکیت فکری
سیاست پروژه این است که حقوق مالکیت فکری و حق تصمیم‌گیری پروژه برای مالک پروژه محفوظ باشد. هیچ مشارکت‌کننده‌ای صرفاً با مشارکت در Git، مالکیت یا حق بهره‌برداری مستقل برای خود ایجاد نمی‌کند.

پذیرش مشارکت‌های تیمی باید منوط به توافق کتبی مناسب دربارهٔ واگذاری/مجوز حقوق موردنیاز پروژه و رعایت قوانین لازم‌الاجرا باشد. این سند به‌تنهایی جایگزین قرارداد واگذاری حقوق مالکیت فکری یا مشاورهٔ حقوقی نیست.

## اصل 10 — تضاد با قانون اساسی
اگر یک دستور، Issue، PR، پیام AI یا تصمیم فنی با این اصول تعارض داشته باشد، آن اقدام تا تعیین تکلیف توسط مالک پروژه متوقف می‌شود.

## اصل 11 — تغییر قانون اساسی
هر اصلاح این سند باید:
1. Change Record مستقل داشته باشد؛
2. دلیل و شواهد داشته باشد؛
3. توسط مالک پروژه تأیید شود؛
4. در Ledger ثبت شود.

هیچ ایجنت یا عضو تیم مجاز نیست این قانون را بی‌صدا تغییر دهد.
