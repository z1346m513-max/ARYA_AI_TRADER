# پروتکل اجرای دستورهای هوش مصنوعی در ARYA_AI_TRADER

**شناسه سند:** ARYA-GOV-AI-EXEC-001  
**نسخه:** 1.0  
**وضعیت:** پیشنهادی؛ در انتظار بازبینی و تأیید مالک پروژه  
**مخزن مرجع:** https://github.com/z1346m513-max/ARYA_AI_TRADER

## 1. اصل حاکم

هر دستور اجرایی باید یک شناسه یکتا (Instruction ID) و یک سند مرجع در مخزن GitHub داشته باشد. هر عامل یا هوش مصنوعی، مستقل از نام، شرکت، مدل یا پلتفرم خود، با دریافت **شناسه دستور** یا **پیوند مستقیم سند دستور** موظف است این پروتکل را دنبال کند.

نام ابزار هوش مصنوعی، متن پیام‌رسان یا توضیح شفاهی جایگزین سند مرجع نیست. در صورت اختلاف، آخرین نسخه معتبر سند دستور در مخزن و تصمیمات مصوب مالک ملاک است.

## 2. قالب شناسه و محل ثبت

- شناسه هر دستور: `ARYA-INS-YYYYMMDD-NNN`
- محل پیشنهادی اسناد دستور: `docs/instructions/`
- محل گزارش‌ها: `docs/reports/`
- محل ثبت تغییرات: `docs/changes/` و `docs/governance/CHANGE_LEDGER.md`
- هر دستور باید به نسخه/Commit مبنای خود اشاره کند.
- شناسه‌ها تکراری یا قابل استفاده مجدد نیستند.
- سند دستور باید شامل وضعیت، مسئول، تاریخ ایجاد، دامنه، وابستگی‌ها، خروجی‌ها، معیار پذیرش و محدودیت اختیارات باشد.

## 3. روند اجباری هر هوش مصنوعی پس از دریافت شناسه یا لینک

1. سند دستور را در مخزن رسمی باز و کامل مطالعه کن؛ فقط به عنوان یا خلاصه آن اکتفا نکن.
2. شناسه، نسخه، وضعیت و پیوند سند را بررسی کن.
3. اسناد مرتبط، تصمیمات ثبت‌شده، گزارش مرحله قبل، PRها و محدودیت‌های پروژه را بخوان.
4. اگر سند وجود ندارد، قابل دسترسی نیست، وضعیت آن «پیش‌نویس/لغوشده/بسته‌شده» است یا با تصمیم مصوب تعارض دارد، اجرا را شروع نکن؛ موضوع را گزارش و درخواست شفاف‌سازی کن.
5. قبل از اجرا، در همان Issue یا PR یا گزارش GitHub اعلام کن که دستور را دریافت کرده‌ای؛ مسئولیت، برداشت از دامنه، خروجی‌ها و معیارهای پذیرش را خلاصه کن.
6. فقط وظایف و اختیارات صریحاً مجاز در سند را انجام بده. فرض نکن که دسترسی فنی به معنی مجوز استفاده از آن است.
7. کار را در Branch مستقل انجام بده و تغییرات را از طریق PR ارائه کن؛ مستقیماً در `main` ننویس.
8. تست‌ها را اجرا و شواهد واقعی را ثبت کن. نتیجه اجرا نشده یا غیرقابل تکرار را «تأییدشده» اعلام نکن.
9. گزارش نهایی را با ارجاع به Instruction ID، Commit، PR، فایل‌های تغییرکرده، تست‌ها، نتایج، محدودیت‌ها و موارد باز در GitHub ثبت کن.
10. تا زمان تأیید مالک/ناظر، مرحله را «تکمیل‌شده و تأییدشده» تلقی نکن.

## 4. قواعد واگذاری موازی به چند هوش مصنوعی

- هر مأموریت باید یک مسئول اصلی (Primary Owner) داشته باشد.
- سایر همکاران می‌توانند مأموریت فرعی مستقل با شناسه جداگانه دریافت کنند.
- دو عامل نباید بدون هماهنگی روی یک فایل، شاخه یا جزء مشترک تغییر هم‌زمان اعمال کنند.
- عامل بازبین (Reviewer) باید تا حد امکان از عامل مجری متفاوت باشد.
- مسئول اصلی موظف است خروجی همکاران فرعی، وابستگی‌ها و تعارض‌ها را یکپارچه و مستند کند.
- همه همکاران باید از همین پروتکل استفاده کنند؛ این سند وابسته به Manus، Z.ai یا ابزار خاصی نیست.

## 5. کنترل نسخه و ترتیب تقدم

در صورت تعارض، ترتیب زیر رعایت شود:
1. تصمیم صریح و جدیدتر مالک پروژه که در GitHub ثبت شده باشد؛
2. سند دستور اجرایی معتبر و آخرین نسخه آن؛
3. اسناد تصمیمات معماری و Change Recordهای تأییدشده؛
4. گزارش‌ها و پیشنهادهای همکاران؛
5. پیام‌ها یا برداشت‌های شفاهی و غیرثبت‌شده.

هیچ عامل مجاز نیست با تفسیر شخصی، تصمیم مالک یا معماری مصوب را بی‌صدا تغییر دهد. تعارض باید پیش از اقدام گزارش شود.

## 6. محدودیت‌های نیازمند تأیید مالک

بدون تأیید صریح و ثبت‌شده مالک پروژه، هیچ عامل مجاز نیست:
- PR را به `main` ادغام کند یا مستقیماً `main` را تغییر دهد؛
- استقرار عملیاتی یا اتصال به حساب معاملاتی واقعی انجام دهد؛
- مهاجرت برگشت‌ناپذیر یا حذف انبوه داده اجرا کند؛
- اطلاعات انبوه را به فضای ابری منتقل یا حذف کند؛
- هزینه، اشتراک یا سرویس پولی جدید ایجاد کند؛
- اعتبارنامه، کلید API یا داده محرمانه را افشا یا در Git ثبت کند؛
- معماری، دامنه، بودجه یا اولویت مصوب را تغییر دهد؛
- روی رایانه یا زیرساخت مالک عملیات نصب/تغییر پرریسک انجام دهد.

برای این اقدامات، پیشنهاد شامل دلیل، دامنه، ریسک، هزینه، روش بازگشت و اثر بر سامانه ارائه و تا اخذ مجوز متوقف شو.

## 7. قالب گزارش اجباری

هر گزارش باید این موارد را داشته باشد:
- Instruction ID و لینک سند دستور
- نام/شناسه عامل مجری و عاملان فرعی
- وضعیت و تاریخ شروع/پایان
- خلاصه دامنه و موارد انجام‌شده
- Branch، Commit SHA و PR URL
- فایل‌ها و اجزای تغییرکرده
- فرمان‌ها/روش‌های تست و نتیجه واقعی هرکدام
- شواهد قابل بازبینی و محدودیت‌های محیط اجرا
- خطاها، ریسک‌ها و موارد حل‌نشده
- انحراف از دستور و دلیل آن (در صورت وجود)
- تصمیم موردنیاز از مالک
- خودارزیابی و وضعیت پیشنهادی: نیازمند اصلاح / آماده بازبینی / تأییدشده

## 8. وضعیت‌های مجاز دستور

- `DRAFT`: پیش‌نویس؛ اجرای کار مجاز نیست.
- `READY`: دستور تأیید و برای اجرا آماده است.
- `IN_PROGRESS`: اجرا آغاز شده است.
- `BLOCKED`: به علت دسترسی، تعارض، وابستگی یا تصمیم مالک متوقف است.
- `NEEDS_REVISION`: خروجی نیازمند اصلاح است.
- `IN_REVIEW`: خروجی برای بازبینی ارائه شده است.
- `APPROVED`: معیارهای پذیرش تأیید شده‌اند.
- `CLOSED`: مأموریت طبق مجوز بسته شده است.
- `CANCELLED`: دستور لغو شده است.

عامل مجری به‌تنهایی مجاز نیست وضعیت را به `APPROVED` تغییر دهد.

## 9. متن استاندارد ارجاع برای هر هوش مصنوعی

«لطفاً دستور با شناسه **[INSTRUCTION_ID]** را از پیوند رسمی زیر در مخزن ARYA_AI_TRADER دریافت و اجرا کن: **[GITHUB_INSTRUCTION_URL]**.

پروتکل `docs/governance/AI_EXECUTION_PROTOCOL.md` را نیز رعایت کن. پیش از اجرا، نسخه و وضعیت دستور، سوابق مرتبط و اختیارات خود را بررسی کن. اگر دستور معتبر و آماده اجراست، کار را فقط در محدوده مجاز، در Branch مستقل انجام بده؛ تست‌ها و شواهد را ثبت کن و گزارش و PR را به همان دستور پیوند بده. اگر سند در دسترس نیست، ابهام یا تعارض دارد، یا مجوز کافی وجود ندارد، اجرا را متوقف و موضوع را در GitHub گزارش کن. هیچ ادعای انجام یا تست موفق بدون مدرک ارائه نکن و بدون تأیید مالک، Merge یا اقدام برگشت‌ناپذیر انجام نده.»

## 10. وضعیت این سند

این فایل در یک Branch مستقل برای بازبینی ارائه می‌شود. تا پیش از تأیید مالک و ادغام مجاز، آن را سیاست نهایی و لازم‌الاجرا تلقی نکنید. این سند به‌تنهایی مجوز اجرای هیچ مأموریت فنی یا تغییر در سامانه نیست.
