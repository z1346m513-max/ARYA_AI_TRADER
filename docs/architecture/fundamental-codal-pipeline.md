# طراحی ماژول بنیادی و Provider کدال

**وضعیت:** طرح معماری قابل پیاده‌سازی؛ اتصال زنده تا دریافت مستندات/مجوز دسترسی منبع فعال نمی‌شود.  
**دامنه:** داده‌های افشا و صورت مالی شرکت‌های بورسی ایران؛ نه دادهٔ OHLCV.

## ۱. تصمیم‌های طراحی

1. **کدال منبع اولیهٔ حقیقت برای افشای شرکت‌ها باشد.** صفحهٔ عمومی [کدال](https://codal.ir/) جست‌وجوی اطلاعیه را با فیلترهایی مانند نماد، گروه/نوع اطلاعیه، موضوع، شماره پیگیری، تاریخ، دوره و وضعیت حسابرسی فراهم می‌کند. همان صفحه خدمات داده‌ای «سدرا» را به‌عنوان REST/JSON و سرویس ارزش‌افزودهٔ رایان‌بورس معرفی می‌کند. بنابراین پیش از هر استخراج برنامه‌ای، مسیر اول باید گرفتن مستندات، شرایط استفاده، مجوز و کلید دسترسی از همین ارائه‌دهنده باشد.
2. **فیبو را بدون مجوز کتبی منبع برنامه‌ای نکنید.** صفحهٔ [قوانین فیبو](https://fibo.ir/apps/tos) صراحتاً استخراج داده و استفادهٔ تجاری بدون مجوز کتبی را ممنوع می‌کند و برخی سرویس‌ها نیز نیازمند اشتراک‌اند. از فیبو می‌توان به‌عنوان الگوی تجربهٔ کاربری و فهرست سنجه‌ها استفاده کرد؛ `FiboProvider` فقط پس از دریافت API/مجوز کتبی قابل فعال‌سازی است. از scraping یا endpointهای خصوصی/مستندنشده استفاده نشود.
3. **بازار قیمت و بنیادی دو دامنهٔ داده‌اند.** Provider کدال قیمت/کندل OHLCV تولید نمی‌کند. برای جایگزینی `MockMarketProvider` در بازار سهام، باید Provider مجاز قیمت بازار (برای مثال منبع رسمی/قراردادیِ سازگار با بورس ایران) جداگانه فراهم شود؛ دادهٔ کدال به‌تنهایی برای محاسبهٔ اندیکاتورهای قیمت کافی نیست.
4. **Mock حذف نمی‌شود.** درایور Mock برای آزمون قطعی، کار آفلاین و توسعه باقی می‌ماند. تغییر در `configs/providers.yaml` با انتخاب درایور انجام می‌شود و آزمون‌ها نباید به اینترنت وابسته شوند.

## ۳. قراردادها و مدل‌های داده

### `CodalProvider`

عملیات پیشنهادی، همگی read-only و قابل صفحه‌بندی:

```python
class CodalProvider(ABC):
    @abstractmethod
    def search_announcements(self, query: AnnouncementQuery) -> Page[Announcement]: ...

    @abstractmethod
    def fetch_announcement(self, tracking_no: str) -> AnnouncementDetail: ...

    @abstractmethod
    def fetch_statement(self, version_id: str) -> list[FinancialStatement]: ...
```

`AnnouncementQuery` باید فیلترهای واقعیِ منبع را نگه دارد: نماد، نوع/گروه اطلاعیه، بازهٔ انتشار، سال مالی/طول دوره، حسابرسی، اصلی/اصلاحی و تلفیقی/غیرتلفیقی. شناسهٔ پیگیری کدال را به‌صورت رشته نگه دارید؛ شناسه‌های متنی ممکن است leading zero یا قالب غیرعددی داشته باشند.

### مدل افشا و صورت مالی

- `Announcement`: شناسه/شمارهٔ پیگیری، نماد، نام ناشر، کد/نوع نامه، عنوان، زمان انتشار منبع، URL مرجع و timestamp دریافت.
- `AnnouncementVersion`: نسخه، اصلاحیه‌بودن، وضعیت پردازش، serial مرجع، hash payload، parser/version و زمان انتشار. نسخهٔ قبلی حذف یا overwrite نشود.
- `FinancialStatement`: نوع صورت (ترازنامه، سودوزیان، جریان نقد)، دورهٔ پوشش به ماه، تاریخ/ستون‌های دوره، حسابرسی و تلفیقی‌بودن، واحد و ضریب مقیاس، شناسهٔ نسخه و روش استخراج.
- `StatementRow`: عنوان خام فارسی، عنوان نرمال‌شدهٔ اختیاری، ترتیب، سرستون‌بودن و مقدارهای هر ستون. هم عنوان خام و هم مقدار خام باید برای audit محفوظ بمانند.
- `MetricObservation`: نام سنجه، مقدار، واحد، ارز، دورهٔ آغاز/پایان، زمان در دسترس‌شدن عمومی، `observed_at`، منبع، نسخهٔ صورت، روش/نسخهٔ فرمول، کیفیت و flags حسابرسی/تلفیقی.

مقادیر گمشده را صفر نکنید. `value=null` همراه با `missing_reason` از صفر واقعی، تقسیم بر صفر، نامرتبط‌بودن سنجه و خطای parser تفکیک شود. همهٔ زمان‌ها timezone-aware باشند؛ `published_at` با `fetched_at` یکی نیست.

## ۴. خط لولهٔ پردازش بنیادی

```text
API مجاز کدال
  → دریافت صفحه‌ای / resume از checkpoint
  → ذخیرهٔ payload خام و hash
  → تشخیص نسخه و اصلاحیه
  → نرمال‌سازی واژگان و واحد/مقیاس
  → اعتبارسنجی جمع‌ها، دوره و ستون‌ها
  → استخراج سنجه‌های بنیادی با نسخهٔ فرمول
  → سنجش تازگی/کامل‌بودن/کیفیت
  → FundamentalAnalyzer → SectionScore [-1, 1]
  → ScoringEngine فعلی → Recommendation توضیح‌پذیر
```

سنجه‌های قابل‌ارزیابی با توجه به دادهٔ موجود: `P/E`, `D/E`, `ROE`, `ROA`, `ROI`, current/quick/cash ratios, `P/B` و سنجه‌های وجه نقد عملیاتی. `P/E`، `P/B` و نسبت‌های قیمت به دارایی به قیمت هم‌زمان و تعدیل‌شده نیاز دارند؛ کدال به‌تنهایی قیمت را تأمین نمی‌کند. نام‌گذاری/تعریف‌هایی مثل `P/A` را تا روشن‌شدن فرمول منبع در محاسبات ARYA فعال نکنید. `Altman Z-score` را فقط با فرمول مستند، واحد پول همسان و مجموعهٔ اقلام کامل محاسبه کنید.

هر `SectionScore.details` باید حداقل سنجه‌های مؤثر، جهت اثر، وزن‌ها، منابع، زمان انتشار/دریافت، نسخهٔ گزارش، دلایل حذف سنجه و کیفیت را ثبت کند. `confidence` را از تازگی، پوشش سنجه‌ها، سازگاری دوره‌ها، کیفیت parser و وضعیت اصلاحیه بسازید؛ آن را با خودِ امتیاز یکی نگیرید.

### نکات محاسباتی که باید در metric dictionary تثبیت شوند

- نسبت‌های ترازنامه‌ای (مانند جاری/آنی) به تاریخ گزارش مربوط‌اند؛ نسبت سودآوری می‌تواند از صورت سود و زیان دوره‌ای باشد.
- برای TTM، جریان‌های دوره‌ای را از فصل‌های سازگار با واحد/دوره جمع کنید؛ اقلام point-in-time ترازنامه را جمع نزنید.
- قیمت و EPS باید تاریخ هم‌ساز و نوع سهم/تعدیل سازگار داشته باشند. در غیر این صورت `P/E` ناموجود باشد، نه اینکه از قیمت و گزارش‌های ناهم‌زمان محاسبه شود.
- برای ROE/ROA نسبت به متوسط موجودی ابتدا/انتهای دوره را مشخص کنید؛ fallback به ماندهٔ پایان دوره باید در `method` ثبت شود.
- نسبت بدهی به حقوق صاحبان سهام باید تعریف بدهی و مدیریت equity منفی/صفر را دقیق کند.
- مقایسهٔ امتیازهای بنیادی فقط در صنعت/مجموعهٔ هم‌سنخ انجام شود. این سنجه‌ها برای رمزارز/فارکس، بدون تعریف تخصصی همان بازار، نباید وارد score شوند.

## ۵. ذخیره‌سازی، تازگی و همگام‌سازی

جداول SQLite پیشنهادی:

| جدول | کلید/کارکرد |
|---|---|
| `codal_announcements` | `tracing_no`؛ مشخصات مرجع اطلاعیه |
| `codal_versions` | `(tracing_no, version_id)`؛ اصلاحیه‌ها، زمان انتشار، hash |
| `codal_statements` | نسخه + نوع صورت + شمارهٔ جدول/صفحه + دوره + واحد/ضریب |
| `codal_statement_rows` | جدول صورت، ترتیب ردیف، عنوان خام/نرمال و مقادیر خام |
| `fundamental_observations` | `(symbol, metric, period_end, source_version, formula_version)` |
| `provider_sync_state` | provider، query scope، cursor/high-water mark، آخرین موفقیت و خطا |

هر صفحه به‌صورت transaction ذخیره شود؛ checkpoint فقط بعد از commit جلو برود. upsert باید idempotent باشد. اصلاحیه، parser جدید یا hash جدید باید قابل بازپردازش باشد. payload خام یا مرجع قابل‌بازیابی آن را برای audit/parser upgrades نگه دارید. retention و ذخیرهٔ متن/فایل تابع مجوز منبع باشد.

زمان‌بندی از قرارداد API و الگوی به‌روزرسانی ناشر پیروی کند؛ polling پرتکرار برای کدال مناسب نیست مگر provider مجاز latency مشخص کرده باشد. برای GETهای امن: timeout محدود، retry با backoff و jitter، رعایت `Retry-After` و rate limit، circuit breaker و log بدون کلید API. در خطای منبع، دادهٔ cache‌شده با برچسب `stale` قابل‌نمایش است اما نباید fresh معرفی شود.

## ۶. انتخاب منبع و جایگزینی Mock

| مسیر | مزیت | هزینه/ریسک | کاربرد پیشنهادی |
|---|---|---|---|
| REST/JSON مجازِ سدرا/رایان‌بورس | مرجع مرتبط با خود سامانهٔ کدال؛ فهرست کدال آن را سرویس دادهٔ ارزش‌افزوده معرفی می‌کند | مستندات کامل، تعرفه، سهمیه، کلید و حق نگهداری/بازنشر باید از ارائه‌دهنده گرفته شود؛ این موارد در بررسی عمومی تأیید نشد | مسیر تولید پیشنهادی اول |
| سرویس ثالثِ دارای قرارداد/API مستند | راه‌اندازی ساده‌تر؛ بعضی سرویس‌ها ساختار صورت و اصلاحیه را از قبل نرمال می‌کنند | هزینه، سقف، پوشش، SLA، اصلاحیه و مجوز ذخیره/نمایش وابسته به قرارداد فروشنده است | گزینهٔ دوم پس از آزمون نمونه و بررسی شرایط |
| دریافت فایل مجاز CSV/XBRL یا ورود دستی | سبک‌ترین جایگزین آفلاین و مناسب تست پذیرش | بدون همگام‌سازی خودکار؛ نیازمند mapping و ثبت provenance | fallback توسعه/آفلاین |
| استخراج مستقیم از HTML کدال یا صفحات بستهٔ فیبو | وسوسه‌انگیز اما شکننده/محدود | تغییر DOM، ضدربات/حساب کاربری و مجوز؛ فیبو صریحاً استخراج بدون مجوز کتبی را منع می‌کند | برای production توصیه نمی‌شود |

### تنظیمات نمونه پس از گرفتن مشخصات واقعی

```yaml
market:
  stock:
    driver: mock          # با provider مجاز قیمت جایگزین می‌شود؛ کدال قیمت نیست
    enabled: true
codal:
  driver: mock            # sedra تنها بعد از دریافت docs و credentials
  enabled: false
  timeout_seconds: 20
  page_size: 100           # مقدار واقعی را مستندات provider تعیین می‌کند
  sync_mode: incremental
fundamental:
  driver: computed_codal
  enabled: false           # تا زمان وجود دادهٔ کافی و آزمون‌شده
  stale_after_hours: 48    # پیش‌فرض نمونه؛ براساس توافق منبع تنظیم شود
```

از `CODAL_API_KEY`/secret store محیط اجرا برای secret استفاده کنید، نه YAML، فایل نمونه، log، test fixture یا Git. آدرس base URL و schema را از مستندات رسمی vendor دریافت کنید؛ endpointهای مشاهده‌شده در وب‌سایت‌های دیگر را به‌عنوان API کدال رسمی تلقی نکنید.

## ۷. مهاجرت مرحله‌ای از دادهٔ Mock

1. **تفکیک قرارداد و fixtures:** `CodalProvider` و مدل‌های disclosure را تعریف کنید؛ mock deterministic برای کدال بسازید. تست‌های جاری OHLCV بدون تغییر باقی بمانند.
2. **دروازهٔ API/مجوز:** از رایان‌بورس/سدرا مستندات، احراز هویت، sandbox/sample response، نرخ، قیمت و حقوق ذخیره/بازنشر بگیرید؛ یا فروشندهٔ ثالث را با همان checklist ارزیابی کنید.
3. **Adapter فقط خواندنی:** اتصال `httpx` با timeout/retry/rate limiter، صفحه‌بندی و خطای typed. هیچ credentialی در کد ثابت نشود.
4. **ذخیرهٔ خام → canonical:** import محدود چند نماد/دوره؛ پس از مقایسهٔ دستی با منبع، mapping و قواعد واحد تثبیت شوند.
5. **Shadow mode:** دادهٔ واقعی را ذخیره و مقایسه کنید، اما در scoring/decision استفاده نکنید. اختلاف، نسخهٔ اصلاحیه، زمان انتشار، nullها و scale را گزارش کنید.
6. **Canary و فعال‌سازی تنظیمی:** فعال‌سازی به‌ازای بازار/Provider، امکان بازگشت فوری به mock، نشانگر source/freshness در CLI و UI، و آستانهٔ حداقل کیفیت.
7. **افزودن به امتیاز بنیادی:** تنها پس از تست محاسبات، بک‌تست بدون نگاه‌به‌آینده و ثبت نسخهٔ formula/weights.

## ۸. آزمون و معیار پذیرش

- قرارداد Provider با fake HTTP transport؛ تمام آزمون‌های CI بدون اینترنت.
- صفحه‌بندی تکراری، درخواست 429/5xx، timeout، 401، schema ناقص و replay پس از checkpoint.
- آزمون سه حالت اطلاعیه: اولیه، اصلاحیه و چند نسخه؛ بررسی عدم overwrite شدن تاریخچه.
- آزمون دوره‌های شمسی/میلادی، تبدیل رقم فارسی/عربی، جداکنندهٔ هزارگان، منفی داخل پرانتز، واحد/ضریب، null و مقیاس‌بندی.
- محاسبهٔ دستی چند نمونهٔ ثابت از صورت‌های مجازشده؛ tolerance و formula version مشخص.
- دادهٔ کهنه/ناقص نباید امتیاز تازه یا اعتماد بالا تولید کند.
- testsِ integration فقط opt-in و با credential محلی؛ secrets در CI عمومی یا log ظاهر نشود.
- در backtest از `published_at` یا زمان در دسترس عمومی استفاده شود، نه صرفاً دورهٔ مالی. این شرط جلوی نشت اطلاعات آینده را می‌گیرد.

## ۹. اتصال به پروژهٔ فعلی

`AryaApp._provider_for_market()` فعلاً Providerهای OHLCV را از `ProviderRegistry` انتخاب می‌کند و `analyze_symbol()` فقط `TechnicalAnalyzer` را اجرا می‌کند. مسیر بنیادی باید افزوده شود، نه اینکه این منطق مخلوط شود:

```text
analyze_symbol
  ├── MarketDataProvider → OHLCV → TechnicalAnalyzer
  ├── CodalProvider → CodalStore → FundamentalCalculator → FundamentalAnalyzer
  ├── SectionScores[] → ScoringEngine (وزن‌بندی موجود در configs/weights.yaml)
  └── Recommendation/Risk؛ همراه source, freshness, confidence, reasons
```

این مسیر با وزن‌های `fundamental` و `codal` در `configs/weights.yaml` سازگار است؛ تا زمانی که دادهٔ واقعی موجود نیست، ScoringEngine باید بخش غایب را از نرمال‌سازی حذف کند، نه اینکه خروجی Mock را به کاربر به‌عنوان تحلیل بنیادی واقعی نشان دهد.
